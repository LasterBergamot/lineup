# Backend: data model, SQLite and Postgres/Supabase

**Data model** (see `documentation/Current-State-Backend.md` for the full ERD and rationale): `team_members` (composite PK `(team_id, user_id)`, role `owner|member` via `CHECK`, `user_id` is a Supabase id with no FK) and `team_invitations` (multi-use links, only `invite_code_hash` = SHA-256 stored, `expires_at`/`revoked_at`, `invited_by_name` = the inviter's display name snapshotted from their token, migration `b7d2e9a41c53`; personal data, so it lives and dies with the row, which is purged a week after `expires_at`) hang off `teams` with `ON DELETE CASCADE`; `teams.repository.create_team` inserts the creator as `owner` in the same commit. The team is the workspace (migration `e5b8c2d41f70`): `teams.owner_id`/`players.user_id`/`saved_lineups.user_id` became `created_by` (audit only, `NOT NULL`), `players.team_id` is required (`RESTRICT`), `saved_lineups.team_id` is the new required workspace FK (`RESTRICT`; unrelated to the soft `source_*` refs), both indexed. Migrations `a3d5f7c91e26`/`e5b8c2d41f70` *deleted* pre-auth ownerless/teamless dev rows and moved lineups into their creator's team: dev-only data, never copy that pattern for real data. `SavedLineup.player_snapshots` is `relationship(..., lazy="selectin")` — async SQLAlchemy can't lazy-load relationships synchronously (raises `MissingGreenlet`), so a relationship is eager or `lazy="raise"`. `Team.players` is `lazy="raise"` with `passive_deletes="all"` (#66): nothing reads a roster through the team, and the ORM must not null `players.team_id` itself when a team is deleted, so the database's `RESTRICT` decides. A `SavedLineup` freezes `team_name`/`opponent_name`/`match_name` as plain text plus nullable soft FKs `source_team_id`/`source_opponent_id` → `teams.id` (`ondelete="SET NULL"`); each `LineupPlayerSnapshot` freezes `name`/`nssz_number`/`cap_number` plus a nullable soft FK `source_player_id` → `players.id` (`ondelete="SET NULL"`). Migration `d9a4c6e81b32` (#64) adds a unique index on `lineup_player_snapshots(saved_lineup_id, cap_number)` (a cap number once per lineup, enforced by the database as well as Pydantic) and indexes on the three soft-reference columns, because Postgres does not index foreign keys itself and each `SET NULL` would scan the table; add an index for any new foreign key. `Player.team_id` and `SavedLineup.team_id` → `teams.id` use `ondelete="RESTRICT"`: team deletion pre-checks for a friendly 409, but the database is the real guard (`teams.repository.delete_team` returns `False` on the `IntegrityError` and the service answers the same 409).

**SQLite foreign key enforcement**: SQLite ignores `ondelete` clauses entirely unless `PRAGMA foreign_keys=ON` is set per-connection — `enable_sqlite_foreign_keys(engine)` in `lineup/db/engine.py` registers a SQLAlchemy `connect` event listener that sets this pragma; both the production engine and the test engine (`tests/conftest.py`'s `db_engine` fixture) call it. Without it, `SET NULL`/`RESTRICT` are silently inert. The listener is gated on `async_engine.url.get_backend_name() == "sqlite"` — `PRAGMA` is SQLite-only syntax and would fail every connection on Postgres.

**Postgres / Supabase connection notes**: there are two Supabase connection flavors. The app at runtime uses the *transaction pooler* (port 6543, user `postgres.<project-ref>`) with just `?ssl=require` on `DATABASE_URL`. `_make_engine_kwargs()` (Postgres only) adds `NullPool` since the pooler already pools, plus `connect_args` turning prepared statements off (`statement_cache_size=0` is asyncpg's own cache, `prepared_statement_cache_size=0` is SQLAlchemy's) and a `prepared_statement_name_func` giving each statement a unique name. All three are needed: without them the pooler hands one server connection to several clients and requests fail with `DuplicatePreparedStatementError` (found only by running against real Supabase; a `prepared_statement_cache_size=0` in the URL alone is NOT enough). An old URL that still carries `&prepared_statement_cache_size=0` is harmless. Also: `created_at` columns are `TIMESTAMP WITHOUT TIME ZONE`, so model defaults must be naive UTC (`_utcnow()` in `lineup/db/models.py`) — SQLite tolerates aware datetimes, asyncpg raises. SQLite-only tests can't catch this class of bug, so re-run the live smoke test (create team/player/saved lineup, delete) against the dev Supabase project after touching models or the engine. Alembic needs the *direct* connection (port 5432) — or the session-mode pooler if there's no IPv6 — because the transaction pooler can't run DDL; for Supabase that URL is `MIGRATE_DATABASE_URL` in the separate git-ignored `backend/.env.migrate` (never in `.env`, which Compose/`task serve` inject into the API's environment), used by `alembic/env.py` (preferred over `DATABASE_URL`) and `task migrate:supabase`. `lineup/db/urls.py:to_asyncpg_url()` rewrites a plain `postgresql://` migration URL (what the dashboard shows) to `postgresql+asyncpg://` and `sslmode=` to `ssl=`; without it SQLAlchemy picks a sync driver that isn't installed (`ModuleNotFoundError`). The `rls_and_least_privilege_role` migration (Postgres-only, guarded no-op on SQLite) enables RLS on every public table incl. `alembic_version`, revokes `anon`/`authenticated`, installs the `lineup_enable_rls` event trigger (skipped with a notice if not permitted; its function has a pinned empty `search_path`, migration `c4e7a1b2d905`, to satisfy Supabase's advisor lint 0011) and creates the non-owner, NOBYPASSRLS `lineup_app` role (DML on the app tables, interim `app_all` policy until #21; migration `a3d5f7c91e26` adds the same RLS/grant/policy for `team_members`/`team_invitations` itself); `task db:create-app-role` (`lineup/db/app_role.py`) then sets its password and rewrites the pooler `DATABASE_URL` to `lineup_app.<ref>`. **A new table's migration must add its own policy and grant the app role nothing more than it needs** — RLS denies the app until a policy exists. `alembic/env.py` skips *type* comparison on SQLite (UUID reflects as NUMERIC); CI's Postgres job compares types. `ENV=production` means "schema is Alembic-managed, skip `create_all`", not "the prod deployment": set it for any real Postgres, including the dev Supabase project (unset, the app would create untracked tables and the next `task migrate` would fail). The app stays on the pooler, not the direct connection: migrations are a separate manual step, the direct host is IPv6-only, and `NullPool` opens a connection per request, which is cheap via the pooler but wasteful directly against Postgres. Switching between SQLite and Postgres: `task db:postgres` / `task db:sqlite` (sed-based, in the Taskfile) comment/uncomment the filled-in pooler `DATABASE_URL` in `backend/.env` and add/remove `ENV=production`; `task db:status` reports the active one. `backend/.env.example` documents all of this; Docker Compose and `task serve` load `backend/.env`, but `task migrate`/`task migrate-new` deliberately don't (they default to SQLite, so a migration never hits Supabase by accident; pass `DATABASE_URL` for one run). Only a dev Supabase project exists so far; prod project, real auth and RLS are tracked separately (see `documentation/Roadmap-Backend.md`).

**Coverage + async SQLAlchemy gotcha**: `coverage.py` needs `concurrency = ["greenlet", "thread"]` under `[tool.coverage.run]` in `pyproject.toml` — SQLAlchemy's async ORM bridges sync calls onto greenlets (`greenlet_spawn`), and without this setting, `coverage` silently drops line hits for code *after* a greenlet-based await resumes (e.g. the line right after `await session.commit()`), even though the code genuinely ran. This looked like a real ~90%-coverage shortfall across every DB-touching module until traced to this missing config.
