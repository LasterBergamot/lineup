# Lineup API

API for creating and managing sports team lineups with PDF export functionality.

## Overview

This project provides a REST API for creating lineups for sports teams (initially focused on water polo in Hungarian leagues) and exporting them as printable PDF documents.

## Project Status

This project is in early development. See `TODO.md` for the current development roadmap.

## Tech Stack

- **Backend**: Python 3.11+
- **Framework**: Flask
- **Dependency Management**: Poetry
- **Testing**: pytest
- **Code Quality**: flake8, black, coverage

## Setup

### Prerequisites

- Python 3.11 or higher
- Poetry (install via `pip install poetry`)

### Installation

1. Configure Poetry to create virtual environments in the project directory (if not already configured):
   ```bash
   poetry config virtualenvs.in-project true
   ```

2. Install dependencies and create the virtual environment:
   ```bash
   poetry install
   ```
   This will create a `.venv` directory in the project root with all dependencies installed.

### Virtual Environment

The project uses Poetry to manage a virtual environment located in the `.venv` directory at the project root.

#### Activating the Virtual Environment

**If the virtual environment already exists** (`.venv` directory is present):

**On Windows (PowerShell):**
```powershell
.\.venv\Scripts\Activate.ps1
```

**On Windows (Command Prompt):**
```cmd
.\.venv\Scripts\activate.bat
```

**On Linux/macOS:**
```bash
source .venv/bin/activate
```

**Using Poetry (works on all platforms):**
```bash
poetry shell
```

#### Setting Up the Virtual Environment

If the `.venv` directory doesn't exist or you need to recreate it:

1. Ensure Poetry is configured to create venvs in-project:
   ```bash
   poetry config virtualenvs.in-project true
   ```

2. Install dependencies (this will create the virtual environment):
   ```bash
   poetry install
   ```

#### Running Commands Without Activating

You can also run commands directly using Poetry without activating the virtual environment:
```bash
poetry run pytest
poetry run black .
poetry run flask run
```

#### Deactivating the Virtual Environment

If you activated it manually (not using `poetry shell`), simply run:
```bash
deactivate
```

If you used `poetry shell`, exit the shell:
```bash
exit
```

## Project Files

### `pyproject.toml`

The `pyproject.toml` file is the main configuration file for the project. It serves multiple purposes:

- **Project metadata**: Defines the project name, version, description, and authors
- **Dependency management**: Lists all production and development dependencies with their version constraints
- **Build system configuration**: Specifies how the project should be built and packaged
- **Tool configurations**: Contains settings for various development tools:
  - `black`: Code formatter configuration (`[tool.black]`)
  - `coverage`: Code coverage settings (`[tool.coverage.run]` and `[tool.coverage.report]`)
  - `pytest`: Test runner configuration (`[tool.pytest.ini_options]`)
  - `mypy`: Type checking configuration (`[tool.mypy]`)

This file is the single source of truth for project dependencies and should be committed to version control. When you add or remove dependencies, you modify this file and run `poetry install` or `poetry add <package>`.

### `poetry.lock`

The `poetry.lock` file is automatically generated by Poetry and contains the exact versions of all dependencies (including transitive dependencies) that were installed. This file ensures:

- **Reproducible builds**: Everyone working on the project gets the exact same dependency versions
- **Consistent environments**: Development, staging, and production environments use identical dependency versions
- **Security**: Locked versions prevent unexpected updates that might introduce vulnerabilities

**Important**: The `poetry.lock` file should be committed to version control for applications (like this project) to ensure all team members and deployment environments use the same dependency versions. Poetry will automatically update this file when you run `poetry install`, `poetry add`, or `poetry update`.

### `.flake8`

The `.flake8` file configures the Flake8 linter for code style and quality checks:

- **Line length**: 100 characters (matches Black formatter)
- **Error codes ignored**: E203, E501, W503 (compatible with Black)
- **Complexity**: Maximum complexity of 10
- **Exclusions**: Virtual environments, cache directories, build artifacts
- **Per-file rules**: Ignores unused imports in `__init__.py` files

This file should be committed to version control to ensure consistent linting rules across all developers.

## Running the Application

### Development Mode

1. Create a `.env` file from the example (if you haven't already):
   ```bash
   cp .env.example .env
   ```

2. Set the environment in `.env`:
   ```env
   FLASK_ENV=development
   ```

3. Run the application:
   ```bash
   poetry run python run.py
   ```

   The application will start on `http://localhost:5000`

4. Test the health endpoint:
   ```bash
   curl http://localhost:5000/api/v1/health
   ```

### Environment Configuration

The application uses the `FLASK_ENV` environment variable to determine which configuration to use:

- **development**: Development mode with debug enabled
- **testing**: Testing mode for running tests
- **production**: Production mode (requires `SECRET_KEY`)

Set `FLASK_ENV` in your `.env` file:
```env
FLASK_ENV=development
```

The application will automatically load the corresponding configuration class (`DevelopmentConfig`, `TestingConfig`, or `ProductionConfig`).

### Production Deployment

For production, use a WSGI server instead of Flask's built-in development server. See the [WSGI Servers](#wsgi-servers) section below.

## Code Quality Tools

The project uses several code quality tools to maintain high standards. These tools are configured and ready to use.

**Configuration files:**
- `pyproject.toml` - Contains configurations for Black, Coverage, Pytest, and MyPy
- `.flake8` - Flake8 linter configuration file

**Quick start - Run all checks:**
```bash
poetry run python scripts/check_all.py
```

This single command runs all code quality checks and tests. See the [Running All Checks](#running-all-checks) section below for details.

### Black (Code Formatter)

Black automatically formats Python code to ensure consistent style across the project.

**Format code automatically:**
```bash
poetry run black app config tests
```

**Check formatting without making changes:**
```bash
poetry run black --check app config tests
```

**Configuration:**
- Line length: 100 characters
- Target Python version: 3.11
- Configuration location: `pyproject.toml` under `[tool.black]`
- Automatically excludes: `.venv`, `__pycache__`, build directories, etc.

**Note:** Black is configured to be compatible with Flake8 by using the same line length (100 characters).

### Flake8 (Linter)

Flake8 checks code style, complexity, and common errors.

**Run linting checks:**
```bash
poetry run flake8 app config tests
```

**With statistics:**
```bash
poetry run flake8 app config tests --statistics
```

**Configuration:**
- Configuration file: `.flake8` (in project root)
- Max line length: 100 (matches Black formatter)
- Error codes ignored: E203, E501, W503 (compatible with Black)
- Max complexity: 10
- Per-file ignores: `__init__.py` files for unused imports (F401)
- Excludes: Virtual environments, cache directories, build artifacts, coverage files

**Note:** Flake8 is configured to work seamlessly with Black by ignoring error codes that conflict with Black's formatting style.

### Coverage (Code Coverage)

Coverage measures how much of your code is covered by tests.

**Run tests with coverage:**
```bash
poetry run pytest --cov=app --cov=config --cov-report=html
```

**View coverage report:**
- HTML report: Open `htmlcov/index.html` in your browser
- Terminal output: Use `--cov-report=term-missing` to see missing lines
- XML report: Generated as `coverage.xml` (useful for CI/CD)

**Coverage configuration:**
- Tracks: `app` and `config` directories
- Excludes: test files, `__pycache__`, migrations, `__init__.py` files
- Configuration location: `pyproject.toml` under `[tool.coverage.run]` and `[tool.coverage.report]`
- Reports generated: Terminal output, HTML (`htmlcov/`), and XML (`coverage.xml`)

**Coverage thresholds:**
- HTML report: Open `htmlcov/index.html` in your browser for detailed line-by-line coverage
- XML report: Used by CI/CD systems for coverage tracking
- Terminal report: Shows missing lines with `--cov-report=term-missing`

**Example output:**
```bash
poetry run pytest --cov=app --cov=config --cov-report=term-missing
```

### MyPy (Type Checker)

MyPy performs static type checking on Python code.

**Configuration:**
